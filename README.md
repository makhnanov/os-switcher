# os-switcher

Аппаратный «автовыбиратель» пункта загрузки в меню GRUB. Плата на ATmega32u4
(Arduino Pro Micro) прикидывается USB-клавиатурой и в нужный момент сама
нажимает стрелки «вниз» и Enter, выбирая нужную ОС в GRUB без участия человека.

Установка — [INSTALL.md](INSTALL.md). Здесь дальше — как оно устроено и почему.

## Как это работает

- Pro Micro (чип ATmega32u4) имеет аппаратный USB и умеет представляться
  хосту как **USB HID-клавиатура**.
- Используется библиотека **HID-Project** и её класс **`BootKeyboard`**.
  Это принципиально: обычная `Keyboard.h` шлёт репорты в *report-protocol*,
  который прошивка (BIOS/UEFI) и загрузчик GRUB на раннем этапе часто не
  разбирают. `BootKeyboard` реализует **HID boot-protocol** — тот самый, что
  понимает хост ещё до загрузки ОС. Поэтому нажатия доходят до меню GRUB.
- После срабатывания триггера плата смотрит на положение выключателя:
  **включён** — шлёт только **Enter** (первый/текущий пункт меню);
  **выключен** — шлёт **4 × «вниз»**, затем **Enter** (альтернативная ОС).
- В уже загруженной ОС плата продолжает следить за выключателем: щёлкнул и не
  вернул назад за 10 секунд — машина уходит в перезагрузку и грузится в другую
  ОС (см. «Перезагрузка по щелчку выключателя»).

Индикация — задний светодиод платы (см. ниже про светодиоды).

## Выключатель выбора ОС

Любой двухпозиционный выключатель (тумблер, клавишный от люстры и т.п. —
это просто контакты). Подключение:

- один провод — на пин **GND** платы;
- второй — на пин **2** (цифровой D2, на шелкографии подписан просто «2»,
  пятый по левому краю от USB-разъёма: TX0, RX1, GND, GND, **2**).
  Не путать с пином «A2» — это другой, аналоговый пин.
- Полярность не важна, внешний резистор не нужен: пин работает в режиме
  `INPUT_PULLUP` (внутренняя подтяжка к HIGH, замкнутый выключатель даёт LOW).

Положение читается **в конце** 15-секундного ожидания, прямо перед нажатиями,
так что щёлкнуть выключателем можно, пока мигает светодиод.

## Перезагрузка по щелчку выключателя

Щёлкнул выключатель в уже загруженной системе — через 10 секунд машина сама
уходит в перезагрузку и грузится в ту ОС, которая соответствует новому
положению. Передумал — верни выключатель назад, пока светодиод часто мигает,
и ничего не произойдёт.

Как это устроено:

1. Плата опрашивает пин D2 в `loop()` (антидребезг 50 мс) и сравнивает
   положение с «исходным» — тем, что было на момент загрузки.
2. Положение изменилось → запускается отсчёт `REBOOT_HOLD_MS` (10 с), всё это
   время RX-светодиод **часто** мигает (0.1 с — визуальное отличие от
   медленного мигания перед нажатиями в GRUB), а на экране висит уведомление
   с обратным отсчётом.
3. Вернули назад до конца отсчёта → отбой, светодиод гаснет, уведомление
   меняется на «Отменено».
4. Отсчёт дошёл до конца → плата шлёт в свой **USB-serial** строку `REBOOT`
   (три раза с интервалом 0.5 с) и зажигает светодиод ровно.
5. Сервис `os-switcher-rebootd` на хосте читает порт и выполняет
   `systemctl reboot` — **штатную** перезагрузку, с корректным завершением
   сессии.
6. ПК уходит в ребут → сброс USB-шины → перевзводится обычный GRUB-триггер →
   плата выбирает пункт меню по новому положению выключателя.

Почему через сервис, а не «плата сама нажимает reboot»: клавиши «перезагрузить
компьютер» не существует. `Ctrl+Alt+Del` в Windows открывает экран
безопасности, в GNOME/KDE — диалог выхода (дальше пришлось бы вслепую
досылать стрелки), а магический SysRq работает только в Linux и жёстко убивает
приложения. Serial-команда + сервис работает одинаково в обеих ОС и завершает
систему корректно.

### Протокол платы и хоста

По одной строке на событие, в CDC-порт платы:

| Строка         | Когда                        | Что делает сервис |
|----------------|------------------------------|-------------------|
| `COUNTDOWN 10` | щёлкнули, пошёл отсчёт (аргумент — секунды) | показывает уведомление с обратным отсчётом, обновляя его раз в секунду |
| `CANCEL`       | вернули выключатель назад, либо ПК уходит в сон/перезагрузку | гасит уведомление («Отменено») |
| `REBOOT`       | отсчёт дошёл до конца        | `systemctl reboot` |

Длительность отсчёта задаёт **плата** (`REBOOT_HOLD_MS`), хост её не знает и
берёт из аргумента `COUNTDOWN` — менять время надо в скетче, в одном месте.

Уведомления в Linux показываются через `notify-send`. Сервис работает от root, а шина
уведомлений живёт в сессии пользователя, поэтому активная графическая сессия
ищется через `loginctl` (`Active=yes`, `Type=x11|wayland`) и `notify-send`
запускается от её владельца. Сессия перепроверяется в начале каждого отсчёта —
на момент старта сервиса (загрузка) её ещё может не быть. Нет сессии или нет
`notify-send` — сервис работает молча, перезагрузка всё равно отрабатывает.

В Windows то же самое делается toast-уведомлением: тост создаётся с data
binding, а раз в секунду `ToastNotifier.Update()` подменяет в нём текст по
тегу — прямой аналог `notify-send -r <id>`. Тосты показываются от имени
готового AppUserModelID Windows PowerShell (свой потребовал бы ярлыка в меню
«Пуск» с прописанным `System.AppUserModel.ID`), поэтому в углу уведомления
будет подпись «Windows PowerShell». Не поднялся toast-API — демон так же
работает молча, а причина уходит в
`%LOCALAPPDATA%\os-switcher\rebootd.log`.

Слежение **выключено**, когда следить незачем: ПК спит (`isSuspended()`),
выключен/перезагружается (`!configured()`) и пока идёт 15-секундное ожидание
GRUB. Поэтому щелчок во время мигания перед выбором пункта меню перезагрузку
не заказывает — он уже учтён самим выбором ОС.

### Сервисы на хосте

Перезагрузку исполняет сервис, свой в каждой ОС. Ставится отдельно от прошивки:

```bash
make install-service      # Linux (systemd + правило udev)
```

```powershell
powershell -ExecutionPolicy Bypass -File host\windows\install.ps1   # Windows
```

Windows-версия работает **от пользователя**, а не службой от SYSTEM: тосты
живут в сессии пользователя, из сессии 0 их не показать, а перезагрузить
машину интерактивный пользователь может и без прав администратора. Поэтому
она ставится задачей планировщика «при входе в систему» — и, соответственно,
не сработает, пока никто не залогинен.

На живой Windows 11 проверены установка, автозапуск задачей планировщика,
поиск своей платы среди двух с общим `VID:PID` (плату различает `iProduct`,
см. `CLAUDE.md`) и сам протокол: щелчок выключателя даёт `COUNTDOWN 10`,
возврат — `CANCEL`. Уведомления и перезагрузка по `REBOOT` вживую не
проверялись.

Пошагово, с проверками и разбором частых граблей, — в [INSTALL.md](INSTALL.md).

### Предупреждение: доверие к плате ничем не подтверждается

Сервис работает от root и перезагружает машину, получив строку `REBOOT` с
любого USB-устройства, у которого совпал VID:PID (`2341:8036`) — то есть
с любой платы на ATmega32u4 со стандартным идентификатором Leonardo.
Ни секрета, ни подписи в протоколе нет: строка `REBOOT` открытым текстом.

Практически это значит, что человек с физическим доступом к USB-порту может
воткнуть свою плату и перезагрузить компьютер. Специально с этим ничего не
делается: у того, кто дотянулся до USB, и так есть кнопка питания, а хуже
внезапной перезагрузки тут ничего не случается — команда одна и жёстко
зашита, произвольные команды по serial не исполняются.

Если этого мало (общий/публичный доступ к машине), в протокол стоит добавить
общий секрет: плата шлёт `REBOOT <токен>`, сервис сверяет токен с файлом,
доступным только root. От подмены самой платы это не спасёт — прошивку можно
вычитать, — но случайную «чужую Leonardo» отсечёт.

### Важно при прошивке

Сервис держит порт открытым, а `arduino-cli upload` дёргает порт на 1200 бод и
ждёт появления загрузчика. `make flash` сам останавливает сервис на время
прошивки и поднимает обратно; если шьёшь вручную — останови его сам.

## Сборка и прошивка

Плата определяется в системе как Arduino Leonardo (тот же чип ATmega32u4),
поэтому FQBN — `arduino:avr:leonardo`.

```bash
CLI=/opt/arduino-ide/resources/app/lib/backend/resources/arduino-cli

# узнать порт
"$CLI" board list

# собрать
"$CLI" compile --fqbn arduino:avr:leonardo os-switcher-sketch

# прошить (порт подставить свой)
"$CLI" upload -p /dev/ttyACM0 --fqbn arduino:avr:leonardo os-switcher-sketch
```

## Про светодиоды на Pro Micro (важно!)

У Pro Micro **нет** пользовательского светодиода на пине 13 (в отличие от
Leonardo). Есть два задних светодиода:

| Светодиод | Пин  | Порт | Логика        |
|-----------|------|------|---------------|
| RX        | D17  | PB0  | инвертированный (`LOW` = горит) |
| TX        | D30  | PD5  | инвертированный (`LOW` = горит) |

Для собственной индикации (мигание) используется **RX-светодиод** через
`LED_BUILTIN_RX`. Помни про инверсию: `digitalWrite(LED_BUILTIN_RX, LOW)`
зажигает, `HIGH` — гасит.

### Почему при выключенном ПК горят оба светодиода, а при загрузке — один

Это и есть ответ на главный вопрос проекта. Оба светодиода RX/TX управляются
**ядром Arduino из обработчика USB-прерывания**: ядро гасит их короткими
импульсами на каждый USB-пакет данных, а в покое они остаются гореть.

- **ПК выключен (S5), но USB под напряжением.** На современных матплатах +5V
  на USB не пропадает в выключенном состоянии, поэтому плата запитана. Но хост
  не общается по шине — USB в состоянии **suspend**, трафика нет →
  ядро ничего не гасит → **горят оба светодиода**.
- **ПК начал грузиться.** USB-контроллер хоста делает сброс шины, энумерацию и
  начинает слать **SOF-пакеты** (Start-Of-Frame, каждую 1 мс) плюс запросы к
  HID. Ядро начинает моргать RX-светодиодом на этот трафик → визуально
  «горит только один».

Другими словами, переход «два горят → один» = **момент, когда хост
проснулся и проэнумерировал нашу клавиатуру**. На это можно и нужно
завязываться.

### Можно ли на это завязываться? — Да, но правильно

Завязываться надо **не на сами светодиоды**, а на то состояние USB, которым они
управляются. Ядро Arduino даёт публичный API:

- `USBDevice.configured()` — `true` после того, как хост завершил энумерацию
  (прислал SET_CONFIGURATION). Это тот самый «просыпается один светодиод».
- `USBDevice.isSuspended()` — `true`, когда шина в suspend (ПК выключен/спит).

Это ровно те же флаги (`_usbConfiguration`, `_usbSuspendState`), что дёргают
светодиоды, только доступные из скетча напрямую — надёжнее, чем читать
состояние ноги светодиода.

## Известная проблема текущего скетча и как её чинить

**Проблема.** Сейчас вся логика (ожидание + нажатия) выполняется в `setup()`,
который отрабатывает **один раз** при подаче питания. Расчёт был на то, что
плата обесточивается вместе с ПК и `setup()` запускается на каждом включении.
Но раз USB питается всегда, `setup()` отрабатывает однажды (при первой
вставке платы) и больше **никогда** — на реальных включениях ПК ничего не
происходит.

**Решение (реализовано в скетче).** Триггерить не по подаче питания, а по
**пробуждению USB-хоста**. Логика живёт в `loop()`: нажатия запускаются по
фронту «стало `configured()`» (то же событие, что зажигает один светодиод),
а перевзводится триггер по **сбросу USB-шины** (`!configured()`) — он
происходит и при включении из выключенного состояния, и при перезагрузке.

Два неочевидных нюанса:

1. **Локаут после срабатывания.** Когда выбранная в GRUB ОС начинает
   грузиться, её ядро сбрасывает USB-шину и заново энумерирует клавиатуру.
   Без защиты этот сброс перевзводил бы триггер и запускал вторую итерацию
   уже в загруженной ОС. Поэтому сбросы шины в течение `REARM_LOCKOUT_MS`
   (15 секунд — ядро сбрасывает шину через 5–15 с после Enter в GRUB,
   так что это значение впритык; при возврате второй итерации — увеличить)
   после нажатий игнорируются.
2. **Suspend триггер не перевзводит.** При выходе из сна (S3) шина
   просыпается без сброса и без энумерации — печатать стрелки в рабочий стол
   после пробуждения не нужно. Реальное включение/перезагрузка всегда
   проходит через сброс шины, так что `!configured()` как условие перевзвода
   покрывает все нужные случаи.

Псевдокод:

```cpp
bool armed = true;
bool hasFired = false;
unsigned long lastFiredAt = 0;

void loop() {
  if (!USBDevice.configured()) {          // сброс шины: включение/перезагрузка
    if (!hasFired || millis() - lastFiredAt > REARM_LOCKOUT_MS)
      armed = true;                       // перевзвод, но не раньше локаута
    return;
  }
  if (armed && !USBDevice.isSuspended()) {
    armed = false;                        // один раз за включение
    // ... мигание-задержка + sendKeys() ...
    hasFired = true;
    lastFiredAt = millis();
  }
}
```

### Про тайминг и GRUB

Триггер срабатывает в момент энумерации USB — это **ранний POST**, ещё до
появления меню GRUB. Меню GRUB появляется позже. Поэтому фиксированную
паузу перед нажатиями надо подобрать так, чтобы «вниз/Enter» попали в **уже
показанное меню GRUB, но до истечения его таймаута**. Слишком короткая пауза —
нажатия уйдут в пустоту (меню ещё нет); слишком длинная — GRUB сам выберет
пункт по умолчанию и загрузится. Текущее значение — 15 с (`INPUT_DELAY_MS`
в скетче), при необходимости подбирается под конкретную машину.

## Требования

- Плата: Arduino Pro Micro (ATmega32u4) или совместимая с USB HID.
- Библиотека: HID-Project (в `~/Arduino/libraries/HID-Project`).
- Arduino CLI/IDE с установленным ядром `arduino:avr`.
